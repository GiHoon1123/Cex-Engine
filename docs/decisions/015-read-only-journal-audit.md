# 체결 코어를 거치지 않고 확정 결과를 조회하기

독립 대사가 Kafka 전달 기록과 별개로 엔진의 확정 결과를 확인하도록 내부 조회 API를 추가했다. 읽기는 별도 연결에서 수행하고 체결 코어의 자료구조·명령 루프·실행 캐시는 변경하지 않았다. 작성일은 2026-10-22다.

## 문제와 기존 동작

엔진은 자체 WAL을 확정한 뒤 결과를 Kafka로 발행했다. 플랫폼에는 영속 수신 키가 있었지만, 플랫폼에서 수신하지 못한 결과를 엔진 기록과 비교할 조회 경로가 없었다. 플랫폼 수신 키만 두 번 읽어서는 엔진 결과의 누락을 찾을 수 없다.

코어에 감사 조회 명령을 넣으면 매칭과 관계없는 이력 조회가 체결 순서를 점유한다. 코어의 오더북·실행 잔액 참조를 공유하는 것도 기존 독점 소유 원칙을 깨뜨린다. 이미 확정된 자체 저널을 별도로 읽기로 했다.

## 검증된 접근과 의존성

[SQLite의 격리 설명](https://www.sqlite.org/isolation.html)은 WAL 모드의 별도 읽기 연결이 커밋된 스냅샷을 읽으며, 쓰기 연결의 미커밋 변경을 보지 않는다고 설명한다. [트랜잭션 문서](https://www.sqlite.org/lang_transaction.html)도 읽기 트랜잭션 동안 동일한 과거 스냅샷을 보는 계약을 명시한다. 확인일은 2026-10-22다.

이미 설치된 rusqlite·Axum·Tokio를 사용했다. 별도 디비·저장 복제·감사 전용 브로커·새 패키지는 추가하지 않았다. 이 조회가 디스크 손실 복제나 변조 방지 서명을 제공하는 것은 아니다.

## 선택과 트레이드오프

| 선택 | 이점 | 비용·제약 |
| --- | --- | --- |
| 자체 저널을 읽기 전용 연결로 조회 | 코어 큐·실행 상태·플랫폼 DB에 의존하지 않음 | 동일 CPU·디스크와 SQLite 저장 엔진 자원을 사용 |
| 최초 확정 순번을 고정해 페이지 조회 | 거래가 계속돼도 대사의 기준 범위가 바뀌지 않음 | 고객 주문 전체의 순간 스냅샷과는 다름 |
| Kafka와 조회가 같은 이벤트 직렬화 사용 | 원본 본문 해시를 직접 비교할 수 있음 | 직렬화 자체를 서로 다른 구현으로 검증하는 구조는 아님 |
| 조회 동시 실행 1개·페이지 제한 | 무제한 디스크 조회 적체를 막음 | 다른 조회는 429를 받고 다시 실행해야 함 |
| 별도 내부 키·기본 비활성 | 고객 경로에 금융 이력을 공개하지 않음 | 운영 키 전달과 접근 경계가 필요 |

SQLite 자체의 저장 동기화는 존재한다. **체결 코어가 조회 세마포어·SQLite 락을 획득하는 경로는 없다.** 읽기 트랜잭션이 오래 유지되면 체크포인트와 자원 사용에 영향을 줄 수 있어 페이지를 짧게 나눈다. 다른 워커로 나눴다는 이유로 자원 경쟁이 사라진다고 주장하지 않는다.

## 내부 API 계약

`GET /internal/audit/results`

| 항목 | 의미 |
| --- | --- |
| `x-engine-audit-token` 헤더 | `ENGINE_AUDIT_TOKEN`과 일치하는 내부 키. 최소 32바이트 |
| `after` | 직전까지 읽은 명령 순번. 기본 0 |
| `through` | 최초 응답에서 정한 확정 상한 |
| `engine_id` | 최초 응답의 엔진 식별자 |
| `limit` | 한 페이지의 명령 개수. 기본 50, 1~100 |
| 응답 `engine_id`, `through` | 전체 대사의 고정 기준 |
| 응답 `next_after` | 이번 페이지에서 확인한 마지막 명령 순번 |
| 응답 `events` | 확정 금융 이벤트의 **원본 JSON 문자열** 배열 |

최초 요청은 `after=0`으로 시작한다. 이후에는 `after`, `through`, `engine_id`를 함께 보낸다. `next_after == through`이면 해당 범위를 다 읽었다. 금융 이벤트가 없는 명령도 순번은 진행하므로 이벤트 배열이 비었다는 이유만으로 조회를 끝내면 안 된다.

공개 호가의 `:market` 이벤트는 이 API의 금융 결과에 포함하지 않는다. 숫자 인덱스의 체결·취소·시장가 종료·전체 거절이 대상이다. 순번·시각·본문은 자체 저널에서 재현한다. 체결 코어에 재실행을 요청하지 않는다.

키 미설정은 503, 인증 실패는 401, 잘못된 요청 범위/페이지 조건은 400, 조회 포화는 429다. 저장 손상·잘못된 엔진 식별자·확정 범위 이탈은 503이며 빈 성공 응답으로 숨기지 않는다. 직렬화한 이벤트 본문 합계는 요청당 4 MiB로 제한한다. 큰 페이지는 줄여서 다시 요청할 수 있지만, 단일 명령의 결과 자체가 한도를 넘으면 별도 운영 판단이 필요하다. 이 한도가 전체 프로세스 메모리 사용량의 상한을 뜻하지는 않는다.

서버의 기본 바인딩은 기존처럼 루프백이다. 컨테이너·다른 호스트로 노출할 때는 사설 통신·서비스 접근 제한·필요한 TLS를 별도로 갖춰야 한다. 조회 키를 브라우저나 고객 API에 전달하면 안 된다. 기존 거래 명령 전반의 서비스 인증까지 완성한 작업은 아니다.

## 구현과 코드

- [감사 조회](../../src/domains/cex/engine/runtime/audit.rs): `SQLITE_OPEN_READ_ONLY`, `query_only`, 읽기 트랜잭션으로 연다. `Store::open`을 호출하지 않아 스키마 생성·저널 모드 변경을 하지 않는다. 검사 합과 순번을 검증한다.
- [출력 직렬화](../../src/domains/cex/engine/runtime/output.rs): `visit_events`가 한 이벤트씩 콜백에 넘긴다. Kafka와 감사 조회가 같은 본문을 사용한다. 체결 목록 전체를 별도 벡터로 복사하지 않는다.
- [Kafka 발행](../../src/shared/kafka/producer.rs): 이미 직렬화한 금융 본문을 같은 토픽·엔진 키로 보낸다. JSON 문자열을 다시 JSON으로 감싸지 않는다. 사용되지 않는 이벤트별 발행 경로와 기본 로컬 브로커에 의존하던 제외 테스트는 제거했다. 성공·장애 발행은 실행 소유 Kafka 회귀로 검증한다.
- [HTTP 등록](../../src/routes/mod.rs), [프로세스 조립](../../src/main.rs): 제어 객체의 저널 경로와 내부 키를 조회 객체에 주입한다.
- [제어 객체](../../src/domains/cex/engine/runtime/engine.rs): 저널 디렉터리의 읽기 참조만 제공한다. 이 접근자는 코어 상태·송신 큐·생명주기 권한을 전달하지 않는다.

Tokio의 기존 블로킹 작업 풀에서 읽기를 수행한다. 조회의 세마포어 허가는 작업이 끝날 때까지 보유하므로 HTTP 요청이 취소돼도 실행 중 읽기의 동시 제한이 먼저 풀리지 않는다. 거래별 스레드 생성은 없다.

## 이해에 필요한 Rust 문법

`Extension<AuditReader>`는 라우터에 주입한 조회 의존성을 꺼낸다. `EngineHandle`을 받지 않으므로 구조적으로 코어 명령을 보낼 권한이 없다.

`spawn_blocking(move || ...)`는 디스크 읽기를 기존 블로킹 작업 풀로 옮긴다. `move`는 경로와 조회 허가의 소유권을 작업으로 넘긴다는 뜻이다. `Arc<Semaphore>`는 조회끼리의 동시 실행 제한이며 거래 상태를 공유하는 락이 아니다.

`visit_events`의 콜백은 Kafka에서는 브로커 확인을 기다리고, 감사에서는 응답 본문을 수집한다. 금액 계산이나 매칭을 다시 하는 함수가 아니다. 검사 합은 저장 손상 검사용이며, 디비 관리자에 대한 전자서명·외부 증적을 대신하지 않는다.

## 작성한 테스트

[감사 조회 테스트](../../src/domains/cex/engine/runtime/audit.rs)의 세 함수는 외부 DB와 체결 코어 없이 실행한다.

| 함수 | 검증 |
| --- | --- |
| `audit_reads_commits_and_fixed_cut_without_core_or_platform_database` | 실제 저널 결과·원본 이벤트·별도 쓰기 연결의 미커밋 꼬리 비가시성·고정 상한·후속 페이지 |
| `audit_rejects_corruption_missing_file_and_wrong_engine_without_mutation` | 없는 파일의 자동 생성 금지·다른 엔진 거부·검사 합 손상 거부·원본 순번 보존 |
| `audit_http_authentication_bounds_and_capacity_fail_closed` | 실제 Axum 요청의 인증·잘못된 페이지·기준 누락·조회 포화 거부 |

[플랫폼 전체 경로](../../../Cex-Platform-Service/src/test/java/dustin/cex/integration/MarketPathTest.java)에서는 실제 Rust HTTP → Java 대사를 실행한다. Kafka 원본 수신 해시·원장·조회 잔고·예약금·체결·수수료가 일치하고, 오류 주입 및 소비 지연은 각각 다른 상태로 기록되는지 확인한다. 별도 JAR 대사 명령의 정상 종료도 포함한다.

## 저장 계약과 한계

저널 형식은 **버전 4 그대로**다. 기록·출력·감사 직렬화의 외부 금융 계약도 유지한다. 기존 서버·디비·저널을 변경하거나 재시작하지 않았다. 플랫폼 원장 테이블과 체결 식별자 변경은 [플랫폼 결정](../../../Cex-Platform-Service/docs/decisions/011-asset-ledger-and-reconciliation.md)을 따른다.

조회는 금융 결과의 원본 근거를 제공한다. 매칭 알고리즘을 다른 구현으로 재검증하거나, 수탁 자산의 실재·블록체인 잔액·최초 반입 잔액의 외부 진실성을 증명하지 않는다. 디스크 손실에 대한 복제·백업은 합의대로 문서상의 필요 조건이다.
